# React 学习与源码专栏：从基础到深入

依据：[文章写作规范](ARTICLE_WRITING_GUIDE.md)、[现有覆盖审计](REACT_COVERAGE_AUDIT.md)。本文规划章节及验收方式，不代表正文已经完成。现有本地文章仍按审阅稿处理。

## 1. 先把路线说清楚

这套内容服务已经会写 JavaScript/TypeScript、但希望系统理解 React 的开发者。基础部分不从安装编辑器开始，而从最容易影响判断的模型开始：组件执行到底意味着什么，状态为什么像快照，身份为什么影响状态保留。

之后逐步进入交互、数据结构、调度、复用与性能，最后再讨论服务端渲染。读完不要求背下所有字段或函数名，而是能够拿到一次异常更新，沿着“输入 → 状态 → 身份 → 工作安排 → 提交 → 浏览器呈现”说明原因、设计实验并判断证据是否充分。

拟设 **7 个系列、27 章**。篇数是当前问题拆分的结果，写作时允许合并或细分，但不得为保留编号牺牲完整解释。每章必须有自己的具体问题和交付物，不能以一段术语列表占位。

| 系列 | 内容 | 进入条件 | 完成后能做什么 |
|---|---|---|---|
| A · 建立正确模型 | 元素、组件、状态、身份 | 会 JS/TS、基本 DOM 和事件 | 预测普通更新，识别状态来源与身份错误 |
| B · 可靠交互 | Hooks、Effect、事件、数据流、竞态 | 完成 A | 写出能清理、能取消、能解释执行顺序的交互 |
| C · Fiber 与协调 | 结构、双缓冲、数组协调、工作与提交 | 完成 A、B；理解链表和引用 | 沿具体节点解释一次树更新 |
| D · 更新与调度 | Hook 队列、Lane、根调度、Scheduler、并发 | 完成 C | 区分入队、选工作、安排回调和实际执行 |
| E · 复用、记忆化与性能 | bailout、memo、Hook 记忆化、订阅、测量 | B 可先读应用部分；原理依赖 C、D | 解释为何重渲染，选择并验证优化手段 |
| F · 服务端与框架边界 | SSR、hydration、流式、缓存与框架 | A、B 必需；C、D 帮助理解 | 分清服务器输出与客户端接管，避免混用版本概念 |
| G · 综合工程 | 故障诊断、性能与正确性证据 | A～E；SSR 场景再加 F | 独立完成一次有证据的定位、修复与复盘 |

推荐完整路线：A → B → C → D → E → F → G。赶时间的应用路线：A → B → E 的案例部分 → G；遇到内部机制问题再回 C、D。本站现有调度总览可作为 C/D 导读，但不能替代前置章节。

## 2. 版本和贯穿项目

### 稳定主线

- 客户端原理与源码实验固定 **React / React DOM 18.3.1**、`createRoot`。使用该 tag 对应的默认 reconciler 路径，不能把其他版本函数混到同一条调用链里。
- Node.js 22、TypeScript 5.7.2作为既有示例基线；各项目的锁文件记录具体工具版本。涉及实验比较必须固定开发/生产模式与 StrictMode 设置。
- 浏览器实验保持单文件可运行入口；复杂项目提供完整目录、依赖、命令、输入、预期结果与测试。
- React 19、React Compiler、Server Components 等版本相关内容，在 F 系列开写前单独核对官方资料并建立独立版本项目。不得把 React 18 客户端源码直接当作这些功能的实现依据。
- 本规划只提出待验证问题，不预先承诺浏览器中间帧、调度次数、性能数字或未来框架行为。

### 贯穿项目：可搜索的任务看板

同一个项目逐步加入任务列表、编辑面板、筛选、异步请求、外部状态订阅和服务端首屏。小实验仍可独立运行，业务命名保持一致，避免读者每章重新理解背景。

| 阶段 | 新能力 | 有意保留的故障 |
|---|---|---|
| A | 展示、编辑、重排任务 | 下标 key 导致编辑状态跟错任务 |
| B | 搜索请求、订阅、表单与事件 | 旧响应覆盖新结果、订阅清理缺失 |
| C | 为原案例建立元素/Fiber/DOM对应图 | 把复用误认为跳过渲染，把render误认为DOM已变 |
| D | 高成本结果列表、紧急输入与延后更新 | transition 内同步重计算仍阻塞 |
| E | 定位重渲染、记忆化、列表缩减与外部 store | 不稳定 props、错误依赖、过度记忆化 |
| F | 服务端生成首屏、客户端接管 | 服务端与客户端输入不一致 |
| G | 汇总复现与证据，完成修复报告 | 相似症状来自不同机制，不能只凭表象归因 |

## 3. 系列 A：建立正确的 React 模型（4 章）

### A1 · 写下 JSX 之后，React 拿到的到底是什么？

**问题**：组件函数、React 元素、Fiber、DOM 为什么不能混成一个东西？

- 从任务卡片 JSX 出发，解释描述对象、组件调用、宿主输出，以及纯渲染的要求；介绍 render/commit 区分但不提前展开调度源码。
- 代码：可运行的元素创建与组件返回实验；列出组件返回 null、Fragment、多个孩子的对照。
- 图：同一个任务的 JSX → 元素描述 → 工作节点 → DOM，说明一对多与没有独立 DOM 的情况。
- 验收：读者能解释“组件执行了为什么不等于 DOM 已改”；不通过访问私有 Fiber 字段证明公开行为。

### A2 · 为什么连续更新三次，结果有时只加一次？

- 建立状态快照、闭包、值更新与函数式更新的模型；在明确的 React 18 createRoot 场景验证批处理，不把 setState 简化成固定同步或异步。
- 代码：三次值更新、三次函数更新、定时回调读取快照的对照；严格区分事件执行、render 日志和提交日志。
- 图：同一回调中的快照与更新顺序。
- 验收：先预测再运行，能解释不同结果；底层队列重放转入 D1，不在这里用伪实现冒充 React。

### A3 · 状态为什么跟错了任务：位置、key 与类型

- 解释同一父级下的身份、稳定 key、下标 key、父 key 和组件函数身份；包含条件渲染与主动重置表单。
- 代码：任务重排后编辑值归属；更换父 key、在父函数内定义子组件的失败对照。
- 图：同一业务对象与同一渲染位置的差异。
- 验收：覆盖保留和重置，说明 key 不负责跨任意父级搬运状态，不把 memo 当作身份修复。

### A4 · 状态放在哪里，才能不靠 Effect 互相同步？

- 用任务筛选与编辑讨论单一数据来源、受控/非受控、派生值、不可变更新、提升状态与 reducer 的适用条件。
- 代码：删除可推导的重复状态；对象原地修改反例；复杂编辑用 reducer 表达转换。
- 图：状态所有者、输入输出与数据流。
- 验收：同一个交互只有清晰的事实来源；解释替代方案的成本，而不声称所有状态都应放到全局。

## 4. 系列 B：写出可靠的 Hooks 与交互（5 章）

### B1 · Hooks 为什么依赖调用顺序？ref 又保存什么？

- 从条件调用导致状态对应关系失效出发解释 Hook 槽位；区分 state、ref、普通局部变量与模块变量。
- 代码：受控失败案例、合法拆组件版本、不会触发更新的 ref；源码层 Hook 链表由 C1/D1接续。
- 图：多次组件执行与 Hook 顺序对齐。
- 验收：能选择合适的存储位置，清楚 ref 不等于响应式状态；规则依据固定版本官方文档。

### B2 · Effect 是同步外部系统，还是“渲染后跑一下”？

- 讲依赖、闭包、setup/cleanup、布局 Effect、开发 StrictMode 检查；区分事件引起的动作与外部同步。
- 代码：订阅建立/清理、错误依赖和计时器泄漏；用日志验证生命周期，不承诺 useEffect 必定晚于 paint。
- 图：更新、清理、重新建立及卸载流程。
- 验收：重复挂载检查后没有泄漏；列明运行模式，避免以开发额外执行推断生产次数。

### B3 · 快速切换搜索词，为什么旧结果覆盖新结果？

- 讲请求生命周期、取消、忽略过期结果、加载/错误状态和卸载；区别取消网络工作与阻止旧结果提交。
- 代码：确定性可控延迟服务或 mock，乱序响应、失败、取消与成功用例；不依赖偶然网速制造竞态。
- 图：两次查询的请求/响应时序。
- 验收：用明确输入证明旧结果无法覆盖新查询；AbortController之外仍解释结果有效性的判定。

### B4 · React 事件怎样到达处理函数？

- 从点击、输入、冒泡与捕获开始，解释 ReactDOM 事件委托、合成事件、原生监听混用及 Portal 的边界；不同事件不能用一个“都代理在根上”概括。
- 代码：嵌套按钮区域、阻止传播、原生监听与 Portal对照；提供浏览器操作步骤。
- 图：实际 DOM 路径与 React 逻辑树路径。
- 验收：说明特定事件与版本，验证观察顺序，区分默认行为与传播，不沿用旧版事件池结论。

### B5 · 组件拆开以后，数据怎样共享才可控？

- 比较 props、组合、Context、reducer、外部 store 的职责；解释 Context 更新与组件订阅关系。
- 代码：任务主题和任务数据分离；过大的 Provider value造成更新扩散的可观察案例。
- 图：所有权与订阅关系图。
- 验收：能解释谁订阅什么、为什么更新，不用“加memo就结束”掩盖Context依赖。

## 5. 系列 C：Fiber、双缓冲与协调（5 章）

### C1 · Fiber不是字段表：沿一个任务追踪结构变化

- 讲 tag/type/key、stateNode、child/sibling/return、memoizedState/updateQueue、lanes/childLanes、flags/subtreeFlags 各自的角色。
- 正文展示固定版本 `FiberNode` 等关键定义；区分函数组件 Fiber 的队列与状态 Hook 队列。
- 图：元素、Fiber、DOM对应关系；表：同一节点在不同阶段的字段变化与修改者。
- 验收：字段不是只列名称；每个关键字段至少连到读写路径或具体场景。内部示意与运行观测分开标记。

### C2 · current 与 work-in-progress 怎样轮换？

- 跟踪首次构建、首次更新建立 alternate、后续重用、字段重置与引用沿用、提交时 root.current切换。
- 正文分段读 `createWorkInProgress`、`useFiber` 和 current切换位置；解释 bailout 与未完成工作相关边界，不声称每轮复制整棵树。
- 图：三轮更新的对象身份与指针连接；可交互教学模型明确不等于 React运行时。
- 验收：能逐步回答“谁被新建、谁被沿用、谁成为current”；未提交工作不得描述成已显示页面。

### C3 · 数组重排时，React怎样复用、移动和删除节点？

- 从单元素匹配过渡到数组顺序扫描、剩余 Map、类型检查、placeChild与lastPlacedIndex；解释空孩子与回退分支。
- 代码：插入、删除、交换、反转、同key不同类型；真实源码在正文就近展示。
- 图：旧索引、新顺序、匹配结果与Placement标记的逐步变化。
- 验收：手算标记并与公开DOM/状态观察对应；不把return null当作删除，不宣称总能得到最少DOM移动。

### C4 · beginWork和completeWork怎样走完一棵树？

- 沿任务列表追踪向下开始、兄弟切换和向上完成；说明宿主创建、属性差异、flags汇总属于哪些路径。
- 源码：工作循环、performUnitOfWork、completeUnitOfWork及本例涉及的begin/complete分支。
- 图：树遍历顺序与工作栈位置；教学步进器展示当前节点和阶段。
- 验收：模型输出与声明遍历路径一致；不把completeWork直接解释成已经提交到屏幕。

### C5 · DOM、ref、布局Effect和普通Effect何时生效？

- 分清before mutation、mutation、current切换、layout以及passive刷新入口；讲错误边界的基本用途并说明未覆盖的内部异常路径。
- 代码：稳定ref、更新、换key、卸载、layout cleanup读取DOM的对照。
- 图：阶段与可观察状态，不把paint硬塞在固定位置。
- 验收：正常与清理路径均有断言；rAF/日志不作为完成绘制的证明。

## 6. 系列 D：从一次更新读懂调度（5 章）

### D1 · 更新进队列后，为什么跳过还能保持顺序？

- 讲dispatch、pending/interleaved、baseState/baseQueue、跳过与NoLane重放、eager条件；区分useState与useReducer路径。
- 贯穿“初始1，先加10再乘2”；真实React最终结果与教学模型过程分别验证。
- 图：环形队列与两轮重放；表：每一步显示状态、基础状态、保留队列。
- 验收：包含非交换操作和错误重放反例，不以模型通过证明所有React并发行为。

### D2 · Lane从哪里来，怎样传播、选择和结束？

- 先解释位集合，再读本例更新的Lane分配、向根传播、pending/suspended/pinged/expired、WIP保留与纠缠、完成后的清理。
- 代码：限定子集的原函数对照；现有六类选择器保留并写清覆盖范围。
- 图：一次更新从产生到清理的集合变化。
- 验收：扩展选择之外的生命周期说明；Hydration/Retry/Offscreen另列边界，不假装全部覆盖。

### D3 · React选了Lane，谁把任务交给浏览器？

- 串起scheduleUpdateOnFiber、ensureRootIsScheduled、已有回调复用/取消与Scheduler安排；区分Sync内部队列和普通回调。
- 代码：固定源码调用链及必要上下文；可取消任务的教学对照，不冒充React Scheduler。
- 图：更新源、根、Scheduler、宿主回调的时序，明确不同优先级体系的映射。
- 验收：一次更新能追到执行入口；不能把Lane优先级、Scheduler优先级和浏览器任务优先级混称。

### D4 · Scheduler怎样排队、让出和继续？

- 在固定环境下阅读任务排序、延时队列、过期、宿主回调、shouldYield与continuation；解释为什么定时器和帧率不能简单等同。
- 实验：有限工作单元与一个长同步单元对照；记录环境与采样方法，不预造5ms切片保证。
- 图：队列状态、回调执行和让出点。
- 验收：能区分React工作单元边界与任意函数内部抢占；实际时延结果附环境与限制。

### D5 · transition为什么能改善输入，却救不了同步死循环？

- 汇总紧急输入、延后结果、重启、陈旧结果与useDeferredValue；介绍Suspense边界下的体验，但不把框架数据获取API当作React公共约定。
- 代码：普通更新、transition、缩减计算量/虚拟化三组；同步重计算反例和确定性加载案例。
- 图：允许中断的render与不应混淆的commit边界。
- 验收：测量输入响应与工作量，区分“安排更合适”与“总计算减少”，没有测量不声称倍数收益。

## 7. 系列 E：复用、记忆化与性能（4 章）

### E1 · props没变，组件为什么还会执行？

- 从React.memo与普通组件对照进入bailout；解释自身state、Context、lanes/childLanes和子树工作。
- 源码、图和实验围绕“跳过当前组件”和“整棵子树不用处理”的差异。
- 验收：至少包含props稳定但Context变化、父跳过但子有工作等场景；自定义比较函数的闭包风险要有反例。

### E2 · useMemo/useCallback到底保存了什么？

- 明确缓存对象、Hook位置、依赖比较、失效、生命周期、计算成本与引用身份；区分语义正确性和性能优化。
- 代码：昂贵计算、函数prop、错误依赖、稳定但不必要的记忆化；固定源码展示依赖判断。
- 图：前后两次Hook数据与依赖变化。
- 验收：移除记忆化后业务仍正确；不把它当永久存储、通用请求缓存或跨实例缓存。

### E3 · 外部store怎样给React提供一致的快照？

- 从订阅与读取时机讨论useSyncExternalStore、快照稳定性、取消订阅及服务端快照入口。
- 代码：最小外部store、返回新对象造成问题的反例、多个订阅者；并发一致性声明须对应真实源码和实验范围。
- 图：订阅、快照检查和更新流程。
- 验收：外部store与Context各自职责明确，不把DOM同步完成等同外部数据一致性全部解决。

### E4 · 先找瓶颈，再决定加memo还是减少工作量

- 使用React Profiler和浏览器性能工具区分组件执行、提交、布局、绘制与长任务；讨论状态下沉、组件拆分、虚拟化、Worker的适用边界。
- 代码：同一任务列表的优化前后版本与固定输入；记录开发/生产模式、设备、样本和指标。
- 图：从实际采样生成的图表，或明确标注的测量步骤示意。
- 验收：性能结论有复现脚本或操作记录，正确性回归仍通过；禁止以一次console计数证明用户体验改善。

## 8. 系列 F：服务端渲染与框架边界（3 章）

### F1 · HTML已经显示，为什么还需要hydration？

- React18独立SSR最小项目；区分HTML生成、资源加载、事件接管和客户端更新。
- 代码：一致输入、时间/随机值不一致、客户端专属状态案例；浏览器验证错误与修复。
- 图：服务器和浏览器时间线。
- 验收：锁定服务端与客户端版本，解释不一致根因，不用suppressHydrationWarning掩盖结构问题。

### F2 · 流式SSR和Suspense怎样逐步交付页面？

- 在React18支持范围内展示流、fallback、客户端接管、取消和失败路径；具体请求协议按本项目限定。
- 代码：可控制的快慢区块、错误及中断；用实际响应和浏览器行为验证。
- 图：服务器输出片段与客户端显示时间线。
- 验收：不把单次慢请求当通用基准，不声称所有数据源都自动支持Suspense。

### F3 · React、Server Components和Next.js缓存分别管什么？

- 独立版本分支，开写前确定React/Next.js确切版本与官方支持关系；列明客户端组件、服务端组件、请求缓存和页面缓存边界。
- 代码：同一读写操作的缓存命中、失效、刷新对照；不能把useMemo与服务端缓存画成同一层。

- 验收：明确缓存对象、key、作用域、失效和权限；结果按指定框架版本复现。本章当前为待定版本，不套用18.3.1内部源码。

## 11. 每章的完成门槛

每章建立一张验收记录，至少包含：读者问题、输入/预期结果、正文承诺、真实源码位置、实际示例、图形路径、验证环境与日期、已知限制、审校意见及修正。

### 内容与源码

1. 从具体问题进入，正文让读者完成一次正常路径与一次反例的推演。
2. 核心判断直接展示真实源码，长函数按逻辑分段；展开源码面板是补充，不能代替关键解释。
3. 展示调用上下文、分支条件、修改对象和返回结果。函数出现过、字段列出来、附过GitHub链接，都不算讲透。
4. 源码固定版本，保留许可；代码节选可逐字核对。教学模型标明删除了哪些机制。

### 代码、图形与运行

1. 完整示例从干净环境按README运行；锁文件、输入与预期输出齐全。
2. 自动测试验证行为与失败路径，不能用“每篇多少小节”替代质量检查。
3. 图码一致；树指针、队列顺序、时间线有明确方向与含义。手机可读，复杂图可放大。
4. 真实React行为、模型行为、jsdom观察和浏览器绘制证据分开记录。
5. 浏览器实验和源码进入离线清单；服务端示例说明依赖安装和运行条件。

- 检查目录、搜索、实验入口、草稿隔离、评论标识、公开阅读与研习权限。
