## 已关闭的 HTTP 语义问题

初版POST不论回放状态都返回202。审稿者用真实HTTP在任务完成后同键重放，得到202加status:succeeded，与正文和RFC9110 §15.3.3的尚未完成语义有冲突。已反馈作者修复：新任务或queued/running回放202，succeeded/failed终态回放200。成功和失败的现有真实场景各加终态回放断言，测试数量仍9项，修后独立重跑全部通过；正文与README同步说明。

## 任务模型机制

核对RFC9110、PG17 SELECT/SKIP LOCKED/advisory locking、Node22.12 fork。接受、事务提交、处理成功三个承诺分开；容量在同一事务级advisory锁里计queued+running，旧key重取不消耗新名额，10请求8接受2拒绝实际成立。claim短事务提交running后释放行锁，长期所有权由worker_id与状态条件承担，SKIP LOCKED不是FIFO或全局空闲证明。

真实提交前SIGKILL无记录，提交后响应前SIGKILL仍可同key恢复一条；API停止Worker仍完成，Worker停止则running保留，没有伪称自动自愈。手工重排先证明夹具自有进程已退出，不把心跳丢失当分布式死亡。完成时条件更新拒绝旧worker；只有纯字符串计算，不声称外部邮件/支付被回滚或恰好一次。COMMIT断链仍可能结果未知，布尔标记不是协议判定器。

## 配额、租约与资源端 fencing

核对PG17行更新/序列、Redis Lua和PTTL、Chubby原论文sequencer。单Redis短脚本原子判断限额，拒绝不增加计数；真实EXISTS过期后再观察新窗口，没有拿睡眠当证明。固定窗口不声称任意滑动窗口上限；故障fail closed，不混同活跃任务容量。

租约与发号在同一PG权威的成功行更新里完成，未把Redis租约后独立发号拼成原子顺序。六连接一个胜者，实际DB时钟到期后接替，旧holder不能续/释新资格；过期不让旧代码消失，无保护资源仍被覆盖。资源条件写保存已接受最大token，拒旧代但允许同代重复，因此与业务幂等、权限分开。明确更高token尚未到达资源前旧token仍可能写，不扩张即时撤销承诺。
