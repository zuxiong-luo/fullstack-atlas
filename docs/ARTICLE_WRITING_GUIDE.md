# 专题文章与专栏写作规范

> 适用于本站所有公开技术文章、专栏章节及配套示例。写新文章、重写旧文章、做内容评审前，都先读这份文档。
>
> 这份规范的目的很简单：读者带着问题来，读完能够解释原理、动手验证，并知道出问题时从哪里查起。不要为了增加篇数，把提纲包装成专业文章。

## 1. 先想读者卡在哪里，再想标题怎么写

本站主要面向有开发经验、希望理解机制并补齐全栈能力的读者。可以假设读者会写基本代码，但不能假设他已经理解本篇要讲的机制。

动笔前，先用几句话回答：

- 读者遇到了什么具体问题？例如“输入框一输入就卡”，比“介绍 React 调度”更容易进入。
- 他已经知道什么？哪些概念需要先补一句解释或链接？
- 看完以后，他能独立做什么？用“实现、解释、定位、比较”来表达，少用“全面掌握”。
- 本篇讲到哪里就够了？哪些问题留给下一篇？
- 用哪个例子贯穿全文？需要交付哪些代码、图形和验证结果？

例如，写 Fiber 前可以这样定目标：

> 你已经会用 useState，但可能还解释不了：为什么一次更新会多次执行组件，而页面只更新一次？这篇沿一次输入更新，看看 React 如何保存待处理工作，以及什么时候才真正修改 DOM。

这段话让读者知道为什么读、需要什么基础、读完能解决什么。不要先写几段“随着技术不断发展”的背景。

## 2. 用自然的话讲清楚，专业性由证据支撑

写作时把自己当成正在带同事排查问题的人。语气可以亲近，但概念和边界必须准确。

- 先描述现象，再解释机制，最后回到现象验证解释。
- 第一次出现术语时给出必要解释，不要连续抛出五个新名词。
- 一段主要解决一个问题，句子之间要有因果关系。
- 可以用“你可能会问”“这里先别急”，但不要每一节都使用同一套过渡句。
- 类比只帮助入门，随后说明真实机制和类比失效的地方。
- 不要把“显然、很简单、众所周知”放在读者最可能困惑的地方。
- 避免“赋能、全面解析、深入浅出、最佳实践”等没有具体内容支撑的表述。
- 不把所有讨论写成面试问答。公开文章围绕理解与实践展开，研习问题另行链接。

表达对照：

| 不够好的写法 | 更适合读者的写法 |
| --- | --- |
| 要做好错误处理和可观测性。 | 如果请求超时，先记录任务 ID、当前阶段和上游耗时。否则你只能看到“失败”，却不知道时间花在排队还是调用服务上。下面给出日志字段和一条失败记录。 |
| async 可以提高并发能力。 | 把函数改成 async 后，同步循环仍会占着执行线程。我们先运行一个阻塞例子，再对比能够让出执行的等待。 |
| Fiber 是可中断的工作单元。 | 递归执行到一半时，怎样保存下次要处理的节点？先看这个小型遍历器如何记录位置，再对照 React 的 Fiber 结构。 |
| 读者可以自行实现一个完整示例。 | 下面先提供能运行的最小版本，再留一个修改任务：把并发数从 2 改成 10，观察耗时和资源占用发生了什么变化。 |

口语化不等于随意：不要用“差不多”“大概就是这样”跳过关键前提，也不要为了亲切而把所有专业术语替换成不准确的比喻。

## 3. 一篇正式文章必须交付什么

下表是验收要求，不是强制的标题模板。每篇可以有自己的叙述顺序，但相关内容必须能找到。

| 要素 | 读者应该得到什么 |
| --- | --- |
| 问题与范围 | 具体问题、目标读者、前置知识、适用版本与不展开的边界 |
| 原理推导 | 输入经过哪些机制产生输出；重要结论为什么成立 |
| 贯穿案例 | 同一个案例随着讲解逐步完善，而不是每节换一个背景 |
| 实现或证据 | 可运行示例、源码路径、协议过程、数据样本或实验观察 |
| 结果验证 | 怎么运行、应该看到什么、看到不同结果时先查哪里 |
| 错误与边界 | 至少一个有代表性的失败、反例或限制，并解释原因 |
| 方案取舍 | 为什么选这个方案，什么时候不适合，替代方案付出什么代价 |
| 回顾与延伸 | 回到开头的问题，用本篇建立的机制回答；给出具体的下一步 |

不能只写“应该限制并发、保证幂等、完善监控”。要展示竞争怎样发生、重复请求怎样进入系统、哪些观测能够区分不同原因。

## 4. 该有代码的地方，就交付代码

以下内容通常必须有代码：

- 解释某个 API 或框架用法时，给出实际调用及上下文。
- 讲执行顺序、闭包、取消、并发等行为时，给出可观察的小实验。
- 讲算法时，给出实现、边界输入与正确性说明。
- 讲系统设计时，至少实现决定正确性的关键路径，例如状态迁移、条件更新、幂等检查。
- 讲源码原理时，正文展示支撑关键结论的真实源码，并解释输入、分支、状态变化与输出；固定版本链接用于追溯，不能替代正文解释。

每个代码块都要有用途：它要验证哪个判断？读者应该看哪几行？运行后应该观察什么？不要让代码块成为装饰。

### 代码必须明确标记类型

| 类型 | 要求 |
| --- | --- |
| 可直接运行 | 给出版本、依赖、文件名、启动命令与预期结果，并实际运行验证 |
| 项目节选 | 链接完整示例与对应文件，说明省略了哪些非关键部分 |
| 原理伪代码 | 明确标注，不声称可以直接运行；重要逻辑仍要完整 |

实践型文章至少提供一个完整的最小示例。关键执行路径不能以 `TODO`、省略号或“自行实现”收尾。不能用一段流程文字冒充可运行代码。

配套示例建议放在 `examples/<article-id>/`。复杂项目可以用独立仓库，但必须能定位到确定的提交或版本。已经采用的合理目录结构可以沿用。

示例说明至少包括：

1. 环境版本与必要依赖，涉及付费服务时说明需要什么配置。
2. 最小文件目录、安装和启动命令。
3. 输入数据、预期输出，以及观察日志或界面的位置。
4. 一条正常流程和一条有代表性的失败或边界流程。
5. 已验证的环境、验证结果，以及尚未验证的部分。

代码要解释设计理由，不要逐行翻译语法。对初学者容易卡住的地方解释充分，对无关样板代码用完整项目链接承接。

JS、TS、React 示例适合在本站实验室运行时，应提供对应入口；Python、Node.js、Next.js、Flutter 等提供本地运行方式，不因为浏览器不能直接运行就省略实现。

## 5. 该用图形的地方，就给读者一张能解释问题的图

图形承担解释任务，不是用来填满页面。遇到下面的问题，应优先考虑图示：

| 读者需要理解什么 | 适合的表现形式 | 图里必须说清楚什么 |
| --- | --- | --- |
| 谁先执行、谁等谁 | 时序图或时间线 | 参与者、先后顺序、等待、中断和恢复位置 |
| 系统由哪些部分组成 | 架构图 | 职责、调用方向、数据流和可信边界 |
| 状态怎样变化 | 状态图 | 初始与终止状态、转换条件、失败和重试路径 |
| 数据结构怎样关联 | 树、链表、内存结构示意 | 节点身份、指针关系、修改前后差异 |
| 算法为什么正确 | 分步图或交互演示 | 当前变量、区间、不变量与每步变化 |
| 坐标或图形怎样变化 | 坐标图与渲染对照 | 坐标系、单位、变换顺序与结果 |
| 两种方案的差异 | 对照图、表格或实测图表 | 相同前提、比较维度、数据来源与限制 |
| 如何实际操作或排查 | 有标注的截图 | 关键区域、观察值及据此做出的判断 |

一个检查方法：如果正文连续使用“左边那个节点、再回到父级、接着进入下一层”，读者很可能已经需要一张图。

### 图形的交付规则

- 给图命名，正文说明“为什么看这张图”和“应该注意哪里”。
- 箭头不能只有方向；需要时标注数据、事件、调用或控制关系。
- 不只靠颜色表达含义，使用标签、线型或图例。
- 标明哪些是真实结构，哪些是教学简化。简化不能改变核心结论。
- 图与正文、代码必须一致；修改执行过程时同步修改图。
- 保留可编辑源文件，图片放在稳定的项目路径，不依赖容易失效的临时外链。
- 提供替代文本或文字解释；手机上应能阅读，复杂图允许放大或横向查看。
- 实测图表必须带单位、环境、样本与测量方式；没有测量就标注为示意，不虚构曲线和数字。
- 发布前确认站点真的渲染了图。把 Mermaid 源码或图片路径显示在页面上，不算完成图示交付。

普通流程图可用 Mermaid 或 SVG；理解过程需要调整参数时，使用交互演示；表现真实性能结果时，使用可复现数据生成图表。无需为了满足数量要求给每篇文章强塞一张图。

## 6. 原理要推导，结论要有来处

尽量沿着“现象 → 假设 → 机制 → 实验 → 结论”的顺序建立理解，具体顺序可按主题调整。

- 框架内部实现固定到具体版本、tag 或 commit，并给出可追踪源码链接。
- 把稳定概念、版本行为和教学简化分开说明。
- 关键事实优先核对官方文档、规范、论文和源码；把引用放在对应论述附近。
- 文末可以汇总资料，但不能只列几个官方首页就认为已提供证据。
- 自己的推断写明推断依据；项目经验写明实际负责范围。
- 不编造性能收益、生产事故、用户规模、团队经历或实验结果。
- 不把某个实现选择写成唯一正确方案，解释适用条件和替代方案。

性能或评测结果至少记录：环境、版本、输入规模、运行方式、指标定义和样本情况。调参过程与最终测试尽量分开，不能只展示最好的一次结果。

## 7. 专栏要连续交付，不只是连续编号

专栏先确定目标读者、最终成果和章节依赖，再安排篇数。不要先定“八篇”，然后为每篇找五个小标题。

每章都要回答：

- 这一章接着上一章的什么结果继续？
- 这次新解决什么问题？为什么现在需要它？
- 哪些文件、结构或行为发生了变化？
- 读者完成后怎样验证？
- 仍然缺什么，下一章为什么要继续？

工程专栏应提供逐章可追踪的示例目录、提交或 tag，不能只在每篇开头反复提到同一个“贯穿项目”。原理专栏可以由一组递进实验组成，不必强行构造大型业务项目。

例如，Agent 知识库助手专栏需要逐步交付：模型调用服务、工具执行器、文档入库与检索、任务恢复、记忆管理、评测脚本、安全验证和部署说明。写“请自行准备一个评测集”不能代替本章应提供的示例用例和评分实现。

## 8. 篇幅和结构服从问题，不服从模板

| 类型 | 建议正文规模 | 读者预期 |
| --- | --- | --- |
| 速览、技术短记 | 800～2,000 字 | 一个小问题或一份明确标注的导读 |
| 独立技术专题 | 3,000～6,000 字 | 原理、实现、验证形成完整解释 |
| 专栏核心章节 | 5,000～10,000 字 | 深入机制、连续案例、实验和失败分析 |
| 项目实战、源码分析 | 依主题确定，必要时拆篇 | 可追踪的工程成果或源码证据 |

这些是编辑预期，不是字数考核。两千字已经讲透的问题不要注水；一万字还在堆概念也不能通过。代码和图形不按凑字数的方式计入正文。

不要机械统一章节数、代码块数量、参考资料数量或阅读时间。阅读时间应根据实际内容估算；实验耗时单独说明。涉及全新理解任务时再拆篇，不为了增加篇数拆散同一条推理链。

当前未达到正式文章标准的内容，可以标注为“概览”“导读”或“待完善”。已有内容没有达到标准，不构成新文章降低标准的理由。

## 9. 不同技术方向的最低深度

| 方向 | 必须交代的核心内容 |
| --- | --- |
| React | 更新过程、状态与树结构、运行行为；源码主题固定版本，并给出实验与结构或时间线图 |
| Next.js | 组件边界、首次访问与导航流程、指定版本的缓存行为，以及可运行的读写案例 |
| Node.js / Python | 并发模型、资源生命周期、取消与异常、容量边界及可运行验证 |
| RN / Flutter / Electron | 分别解释各自的执行、渲染、通信与权限模型，用实际案例比较，避免只列优缺点 |
| WebGL | 完整绘制路径、必要数学解释、坐标图和可运行渲染结果；清屏不能替代三角形渲染教程 |
| 安全 | 威胁模型、信任边界、受控复现、修复验证与仍然存在的风险 |
| 算法 | 约束、朴素解、推导、正确性或不变量、复杂度、边界测试和适合的分步图 |
| 数据库 / 分布式 | 并发时序、失败窗口、一致性前提、关键实现和恢复验证 |
| Linux / Kubernetes | 现象、命令、输出、判断依据与下一步排查分支，不只给命令清单 |
| AI / Agent | 可运行流程、数据样本、失败案例、评测口径、成本和权限边界 |

这是主题相关要求，不意味着每篇文章要讲完整个领域。先缩小标题承诺，再把范围内的问题讲完整。

## 10. 写作与发布流程

1. **确定读者问题。** 写出目标、前置知识、版本、范围与预期成果。
2. **验证素材。** 阅读相关源码与一手资料，确认示例能够支持结论。
3. **设计解释过程。** 先列案例、实验、图形与推导，再安排章节。
4. **完成示例与图形。** 重要实践先跑通，避免写完才发现无法复现。
5. **写正文。** 用自然语言连接现象、机制与结果，解释关键选择。
6. **站在读者的位置重读。** 从提供的命令和输入开始，检查是否存在被作者默认为理所当然的步骤。
7. **核验事实和呈现。** 检查代码、图形、引用、版本与页面效果；手机上的代码和图也要能看。
8. **按任务要求提交发布。** 写明新增或修改范围及验证结果；如本次要求只是草稿或标准文档，不自动改写其他文章。

文章建议记录：固定 ID、内容类型、完成状态、适用版本、最后核验日期、前置知识、阅读与实验耗时、示例位置和参考资料。尚未有对应字段时，不要伪造已有能力；必要时再扩展内容模型。

当前文章数据主要位于 `src/data/articles.ts`、`src/data/expandedArticles.ts` 等文件，专栏关系位于 `src/data/series.ts`。现有段落加代码的模型不能成为降低表达质量的理由：需要多段代码、图、表或实验结果时，应合理扩展渲染能力，而不是删掉必要内容。

## 11. 发布前，替读者问一遍

- [ ] 我知道这篇文章要帮我解决什么问题，标题没有夸大正文。
- [ ] 我能跟上关键推导，新术语出现时有解释。
- [ ] 我不只是读到“应该怎么做”，还知道为什么，以及不这么做会怎样。
- [ ] 该有代码的地方有代码，重要路径没有留给我自行补齐。
- [ ] 该用图解释的地方有图，而且正文告诉我该看哪里。
- [ ] 我能按步骤运行示例，并判断结果是否正确。
- [ ] 我看到了错误或边界情况，而不只是成功演示。
- [ ] 我知道版本、前提、方案代价和不适用的情况。
- [ ] 关键结论能找到依据，实测和示意没有混淆。
- [ ] 作为专栏章节，我知道这一章新增了什么成果、下一章接着做什么。
- [ ] 页面中的代码、图形、链接和目录正常，手机上也能阅读。
- [ ] 读完能用自己的话解释或实践，而不是只记住几个术语。

出现以下任一问题，不能作为“已完成的专业文章”发布：核心承诺没有兑现；声称可运行但缺关键实现；图形与正文矛盾；未经验证却声称有性能收益或生产效果；用增加字数掩盖没有推导与证据。

## 12. 以后让 AI 协助写作时，可以这样下任务

> 请先阅读 `docs/ARTICLE_WRITING_GUIDE.md`。围绕【读者遇到的具体问题】写【专题 / 专栏第几章】，面向【已有知识背景】，使用【版本和环境】。先确定读者能带走什么，再设计贯穿案例、代码与图形。正文要自然、口语化，但保持概念准确；重要机制必须解释原因。该运行的示例实际运行，该画的图真正渲染并检查。不要用流程提纲代替实现，不要为了篇数和字数凑内容。最后按文档中的读者检查表自查，明确哪些已验证、哪些仍有限制。

这段任务描述是起点，不要求每次向读者追问全部字段。已有上下文能确定的内容直接沿用；确实缺少会影响正确性的版本或业务条件时，再说明假设或询问。


## 13. 源码专题的补充验收：读者不用跳出页面才能理解

### 源码在眼前，推导也在眼前

- 对标题承诺的关键机制，在正文展示固定版本的真实代码。长度合适时展示完整函数；较长时按逻辑连续分段，明确省略范围，不删除会改变结论的失败、回退或特殊分支。
- 每段按“为什么看这里 → 真实代码 → 带入具体输入 → 分支与状态变化 → 输出和反例”连接。不要只把代码翻译成中文，也不要把几十行源码贴出来就结束。
- 被调用函数若决定结论，必须继续展示决定性的实现。例如updateSlot只比较key并调用updateElement，不足以单独证明身份复用。
- 原代码、带修改的教学实现和伪代码严格区分。原代码保留类型、注释和分支，解释在代码外；若裁剪，准确标记。保留来源、tag/commit、实际行号和许可。原源码不冒充独立可运行项目。
- 从源文件自动提取、逐字比较代码块；升级版本后重新核对，不让正文与引用各自漂移。

### 专栏覆盖清单

开写前列出“读者要解决的问题、关键函数或机制、所属篇章、目前深度、还缺的验证”。深度区分：未覆盖、仅提及、已推导、已验证。字段名出现过、提供过链接，都不能算讲透。

- 数据结构：字段含义之外，还要有字段被谁读取/修改、前后状态、指针连接、创建和回收/失去引用的边界。
- 调度：至少串起更新入队、根调度、Lane选择、Scheduler安排、工作循环、让出与重启、提交；区分不同层的职责，不能把“可中断”当作过程解释。
- 双缓冲：展示首次建立alternate、后续复用、哪些字段沿用或重置、root.current切换；说明未提交工作与已提交状态的边界，不把双缓冲等同深拷贝或结果缓存。
- 缓存与跳过工作：先明确缓存对象、命中条件、失效条件、生命周期和成本，再解释机制。React.memo、useMemo/useCallback、Fiber复用、请求数据缓存分别讨论，不用一个“缓存”统称覆盖。

每篇保持具体范围，但专栏需要总体地图。必要的推导不能全部推给“下一篇”；确实分篇时给出已存在的阅读入口，尚未写出的明确标为缺口。不能把这张清单变成每篇都要涵盖所有内容的模板。

### 加一道读者检查

读者遮住文末参考资料，能否仅凭正文完成一次正常路径和一次反例的推演？如果必须去GitHub补读关键判断、猜测哪个字段变了或猜测为什么回退，该机制还未达到正文验收要求。
